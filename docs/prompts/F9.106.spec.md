# F9.106 — Asignación de factura a gasto esperado por **mes de pago**

> Continúa la línea F9.82 / F9.99.7 / F9.99.9 (matching comprobante ↔ esperado).
> Audita antes de tocar: `git clone` + `git log --oneline origin/main -1` (HEAD auditado: `57fe9ad`).

## 1. Problema

Al subir la factura del **próximo período** dentro del mes en curso, el sistema la clasifica
como **"pago adicional"** en vez de reconocerla como la **obligación del mes siguiente**.

**Caso testigo (factura Edenor real):**
- Emisión: `2026-07-24` · 1er venc: `2026-08-07` ($136.533,05) · 2do venc: `2026-08-12` ($137.078,95)
- Detectado hoy: "julio + pago adicional" ✗ · Correcto: "agosto + obligación normal" ✓

## 2. Causa raíz (verificada)

`matchPorDestino` (`functions/src/index.ts:478-525`) decide `esAdicional` así:

```ts
// index.ts:296  — mesComp sale de la EMISIÓN
const mesComp = datos.fecha ? datos.fecha.slice(0, 7) : '';
// index.ts:498  — colisión contra el mes de emisión
const yaEnMes = movs.some(m => m.itemEsperadoId === itemId && m.mes === mesComp);
if (!yaEnMes) → { rama: 2 }                 // obligación normal
else          → { rama: 2, esAdicional }    // "pago adicional"   ← FALLA acá
```

Como la emisión (julio) coincide con la obligación de julio ya pagada, `yaEnMes` da `true`
→ `esAdicional`. El mes de **pago** (agosto) nunca entra en la decisión.

Nota: el movimiento creado ya cae en agosto por otra vía
(`preloadBase.fecha = vencimientos[0].fecha`, `Comprobantes.tsx:278` → `mes` en `AltaMovimiento.tsx:232`).
El bug es de **clasificación**, no de destino final — pero la regla de período debe unificarse.

## 3. Decisión de modelado (regla del dueño)

> **"Lo que se paga en X entra en X en resumen mes."**

- **Mes de la obligación / clave de período = mes del PRIMER vencimiento de pago**
  (`vencimientos[0].fecha`). Fallback: emisión (`datos.fecha`) si no hay vencimientos.
- **NO** se usa `periodoFacturado` (consumo) para el bucketing — queda solo como metadato de display.
- El heurístico "principio de mes = este mes / fin de mes = mes siguiente" **no se implementa**:
  el vencimiento ya codifica esa verdad (factura de fin de julio con venc principios de agosto → agosto).

### Tri-rama por mes de pago (reemplaza el `if/else` binario actual)

Sea `mesPago` = mes del 1er vencimiento (fallback emisión), `itemId` = item aprendido:

| Estado de la obligación de `itemId` en `mesPago` | Rama resultante |
|---|---|
| No existe | `rama 2` — crear obligación nueva del mes de pago (caso Edenor) |
| Existe, **impaga** | `rama 1` — reconciliar contra ella (la factura *es* esa obligación; no duplicar) |
| Existe, **paga** | `rama 2` + `esAdicional: true` — segundo cargo real del mismo mes de pago |

## 4. Automatismo graduado por confianza

Respuesta del dueño: *"mostrar a qué gasto esperado y de qué mes, hasta que la confianza sea muy alta."*

`destinos.confianza` ya existe e incrementa +0.1 por confirmación (`index.ts:465`);
`matchPorDestino` ya exige `≥ 0.7` para disparar (`index.ts:494`).

| Rango de `confianza` | Comportamiento |
|---|---|
| `< 0.7` | No auto-propone item (cae a `calcularPropuesta` por texto — sin cambios) |
| `0.7 ≤ c < UMBRAL_AUTO` | **Propuesta con confirmación**: card muestra **item + mes** (ambos editables) |
| `c ≥ UMBRAL_AUTO` | **Auto silencioso**: crea la obligación sin tap, muestra badge de resultado |

- `UMBRAL_AUTO = 0.9` (constante tuneable, junto a `CONFIANZA_INCREMENTO`).
- Nuevo flag en `PropuestaMatch`: `requiereConfirmacion?: boolean` (true en la banda media).
- La card de confirmación **siempre** muestra la confianza actual (para ver cómo sube).

## 5. Cambios concretos

### 5.1 Server — `functions/src/index.ts`
1. Helper `mesDePago(datos): string` → `vencimientos[0]?.fecha?.slice(0,7) ?? datos.fecha?.slice(0,7) ?? ''`.
   Aplica **solo** a docs de obligación (`esObligacionDoc(tipoDocumento)`); para pagos/tickets/transferencias sigue `datos.fecha`.
2. En `matchPorDestino`: usar `mesDePago` para `yaEnMes` (renombrar a `yaEnMesPago`) y ramificar según §3.
3. Agregar `requiereConfirmacion` según §4 (`c ≥ UMBRAL_AUTO` → false).
4. `mesComp` para la ventana `[mes-1..mes+3]` (`index.ts:293-303`): usar `mesDePago` cuando el doc sea obligación (así la ventana de reconciliación se centra en el mes de pago, no en la emisión).

### 5.2 Tipos — `src/types/index.ts` y twin `functions/src/matchLogica.ts`
5. `PropuestaMatch.requiereConfirmacion?: boolean` (mantener el twin en sync — es una regla del proyecto).

### 5.3 Client — `src/vistas/Comprobantes.tsx` + `AltaMovimiento.tsx`
6. Card de confirmación de rama 2 con item aprendido: encabezado explícito
   **"Asignar a: {gasto esperado} · Mes: {mesPago formateado}"**, con `mes` **editable**
   (selector de mes) y el gasto esperado reasignable (reusar el picker existente de `buscarObligacionesAbiertas`).
   Default `mes = mesPago`.
7. Si `requiereConfirmacion === false` → alta silenciosa (llamar `cargarMovimientoDesdeComprobante`
   directo) + badge "Asignado automáticamente a {item} · {mes}".
8. Copy: reemplazar "Pago adicional" por "Obligación de {mes}" salvo en el caso §3 fila 3 (adicional real).
