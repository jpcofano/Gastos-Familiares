## §A — `normalizarEspecie` es un gemelo, y hoy no lo es

La auditoría del §0 encontró que el sufijo de clase (`"YPF - D"`) rompe el match. Pero hay un
problema anterior que el §2 de F9.122 no resuelve solo: **hay dos normalizadores distintos**.

- `functions/src/index.ts:3379` — `normalizarEspecie` — resuelve las especies.
- `src/datos/patrimonioCafci.ts` (final) — `normalizeEspecie` — **escribe las claves del seed** y
  las lee en `calcBenchmark`.

Hoy son idénticos por casualidad. Si el §2 endurece solo el del servidor, las claves escritas por
el seed dejan de coincidir con las que el servidor busca, y el fix falla en silencio — peor que el
bug actual, porque queda plausible. **Los dos tienen que cambiar juntos y quedar declarados como
gemelos**, igual que `evaluarMatchTexto`/`checklist.ts`.

Implementación **idéntica** en ambos archivos:

```ts
// F9.122.1 — GEMELO. La copia canónica es functions/src/index.ts; src/datos/patrimonioCafci.ts la
// espeja. Divergir rompe el mapeo en silencio: el seed escribe claves con una normalización y el
// servidor las busca con otra, y el resultado es "el fondo no tiene el papel" en vez de un error.
// Cada regla responde a una forma observada en CAFCI (auditoría F9.122 §0, 2026-08):
//   "YPF - D"                  — sufijo de clase: la clase no cambia el emisor
//   "Cedear Vista Oil Gas"     — '&' ausente respecto del patrón "Vista Oil & Gas"
//   "Grupo Fciero Galicia - B" — puntuación irregular entre fuentes
export function normalizarEspecie(s: string): string {
  return s
    .trim().toLowerCase()
    .normalize('NFD').replace(/[̀-ͯ]/g, '')
    .replace(/\b(s\.?a\.?u?\.?|s\.?r\.?l\.?)\b/g, ' ')  // razón social, no identifica al emisor
    .replace(/[^a-z0-9]+/g, ' ')                        // & . - , ( ) → espacio
    .trim()
    .replace(/\s+[a-z]$/, '')                           // sufijo de clase de UNA letra al final
    .replace(/\s+/g, ' ')
    .trim();
}
```

**Cuidado con el orden:** el borrado del sufijo va *después* de colapsar la puntuación, si no
`"ypf - d"` no llega a `"ypf d"` y la regex no pega.

**Consecuencia obligatoria:** cambian las claves de `cafciMapping`. Después de aplicar §A + §2 + §3
hay que correr **"Importar mapping seed"** desde la UI para reescribir los 70 docs con las claves
nuevas. Si no se corre, la colección queda con claves viejas huérfanas y el fix no surte efecto.
Anotarlo en el checklist de verificación de F9.122, no dejarlo implícito.

## §B — Base comparable: renta variable argentina de los dos lados

### El problema

Con los datos del §0, la cartera de Galileo tiene 13,5% CEDEAR + 6,3% FCI + 1,7% Resto = **21,5%
que el benchmark descarta**. Ese 78,5% restante se compara contra pesos propios calculados sobre el
**invertible entero**, que incluye ~22% cripto, cash, soberanos y acciones del empleador.

Son dos universos distintos y el número resultante no significa nada. Con los pesos del handoff del
2026-08-05: PAMP propio es 10,3% del invertible pero **~20,5% de tu renta variable AR**; en Galileo
es 11,6% crudo pero **~14,8%** de la porción comparable. La lectura correcta no es "estás en línea",
es "estás bastante más concentrado que el fondo". El fix de unidades de F9.122 no corrige esto — y
al volver los números plausibles, los vuelve peligrosos.

### Decisiones tomadas (marcadas para que Juan las pueda revertir sin leer el código)

1. **Base propia = `bloqueDe(p) === 'accionesAr'`.** Se reusa la función canónica de
   `patrimonioRiesgo.ts`, no se inventa un filtro nuevo. Incluye `tipo: 'accion'` y `tipo: 'cedear'`
   con `pais_riesgo: 'AR'` — o sea VIST entra.
2. **Base fondo = posiciones sin `categoria` LIQUIDEZ / RESTO / RENTA_FIJA**, renormalizadas a 100
   por fondo.
3. **CEDEARs del fondo entran a la base solo si su ticker resuelto está en tu conjunto de renta
   variable AR.** Es asimétrico y hay que decirlo: la regla solo puede *encontrar* solapamiento,
   nunca mostrarte un CEDEAR de riesgo argentino que el fondo tenga y vos no. La alternativa
   —registro propio de riesgo-país por CEDEAR— es un dato que no existe en la app. Sin esta regla,
   VIST sigue apareciendo en "no en fondos" cuando Galileo la tiene al 13,5%.
4. **Se reemplaza la vista sobre cartera total, no se agrega al lado.** Dos denominadores en la
   misma pantalla son dos respuestas a la misma pregunta.
5. **Umbrales de color recalibrados** de 0,05/0,02 a **0,08/0,04**: sobre una base ~2× más chica,
   los deltas son ~2× más grandes y los umbrales viejos pintarían todo en rojo.

### Implementación — `src/datos/patrimonioCafci.ts`

`calcBenchmark` pasa a recibir `Posicion[]` completas (hoy recibe `{ticker, valorUsd}[]`, que pierde
`tipo` y `pais_riesgo`):

```ts
export function calcBenchmark(
  posicionesPropias: Posicion[],
  carteras: CafciCartera[],
  mappings: Record<string, string | null>
): {
  filas: FilaBenchmark[];
  soloenFondos: Array<{ ticker: string; avgFrac: number }>;
  soloEnPropio: string[];
  base: BaseComparable;   // nuevo
}
```

```ts
// F9.122.1 — la base sobre la que se calculan TODOS los porcentajes de este módulo. Se expone
// porque un % sin denominador declarado es una cifra que induce a error, no una medición.
export type BaseComparable = {
  propioUsd: number;          // renta variable AR propia
  propioPctDeCartera: number; // qué fracción del invertible representa
  fondoCoberturaProm: number; // fracción promedio de los fondos que entró a la base
  excluidoFondoProm: number;  // 1 − cobertura: liquidez + resto + renta fija + CEDEAR no-AR
};
```

Pasos dentro de la función:

1. `const propias = posicionesPropias.filter(p => bloqueDe(p) === 'accionesAr')`.
   `totalPropio` = suma de **esas**, no de todas.
2. `const tickersArPropios = new Set(propias.map(p => p.ticker))`.
3. Por cartera: `comparables = cartera.posiciones.filter(pos => !pos.incompleto && pos.ticker
   && pos.categoria !== 'LIQUIDEZ' && pos.categoria !== 'RESTO' && pos.categoria !== 'RENTA_FIJA'
   && (pos.categoria !== 'CEDEAR' || tickersArPropios.has(pos.ticker)))`.
4. `baseFondo = suma de comparables.pesoPct`. **Si `baseFondo < 40`, saltear ese fondo entero** y
   contarlo aparte: renormalizar sobre una base flaca amplifica el ruido en vez de medir. Reportar
   cuántos fondos se saltearon.
5. Peso del fondo por ticker = `pos.pesoPct / baseFondo` (ya fracción — compatible con §1 de F9.122,
   que ya sacó el `/100`; **acá el `/100` desaparece porque `baseFondo` está en la misma escala**.
   Verificalo con un assert: la suma de pesos renormalizados de un fondo tiene que dar 1,0).
6. El promedio sigue siendo sobre **todos** los fondos que entraron (los que no tienen el papel
   pesan 0), consistente con la nota `¹` que agrega F9.122 §1.
