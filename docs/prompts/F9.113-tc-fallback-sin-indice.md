## 1. Síntoma y auditoría

La pantalla *Perfil › Tipo de cambio* muestra, en el lugar del valor del TC:

> `Error al cargar: The query requires an index. You can create it here: https://console.firebase.google.com/…create_composite=Clhwcm9q…`

y abajo `HISTÓRICO (ÚLTIMOS 0)` · `Sin histórico todavía.`

### 1.1 Por qué no hay fallback

`TipoCambio.tsx:41-49` — `recargar()` llama a `cargarTCReciente(10)`; el `.catch` guarda el mensaje crudo en `errorCarga`. Ese estado alimenta **todo** el lado de lectura:

- `TipoCambio.tsx:80-81` — la card imprime `Error al cargar: {errorCarga}` tal cual: texto de dev, sin cortar, sin seleccionar, sin acción. En pantalla de celular el link queda cortado por el borde derecho y **no se puede ni leer ni copiar**.
- `TipoCambio.tsx:51` — `actual = hist[0]` queda `undefined`.
- `hist` queda `[]` → el histórico dice `ÚLTIMOS 0` y `Sin histórico todavía`, que es **falso**: no es que no haya datos, es que la lectura falló. Dos mensajes contradictorios para el mismo hecho.

Una sola consulta fallida deja la pantalla sin valor actual, sin histórico y sin un mensaje que se pueda accionar. Eso es lo que hay que arreglar primero, porque vale para *cualquier* causa del fallo, no sólo esta.

### 1.2 Qué consulta falla

`tcDiario.ts:39-41`:

```ts
query(collection(db, 'tcDiario'), orderBy(documentId(), 'desc'), limit(n))
```

**Ninguna consulta a `tcDiario` en `main` debería necesitar un índice compuesto**: un `orderBy` sobre `__name__` con `limit` se sirve con el índice automático. `firestore.indexes.json` no declara nada de `tcDiario` (y no debería). El comentario de `tcDiario.ts:12-15` documenta que el `where(documentId())` que **sí** requería índice ya se había reemplazado por `desc + startAt` en `tcParaFecha`.

→ Hay una discrepancia entre lo que dice el código de `main` y lo que ejecuta el navegador. Las dos hipótesis, en orden de probabilidad:

- **(a) Bundle viejo en el cliente.** El error coincide con el patrón de la versión anterior de esa consulta. La PWA puede estar sirviendo JS cacheado.
- **(b) La consulta que falla es otra**, de otra pantalla o de código que todavía no auditamos, y ésta sólo es la que muestra el mensaje.

**No inventar un índice para "que ande".** El texto completo del error dice colección y campos exactos; hasta tenerlo, cualquier índice es una suposición. Cómo obtenerlo, en orden:

1. Recargar en **incógnito** (desktop, Hosting URL). Si el error desaparece → era (a), bundle cacheado, y no hay nada que arreglar del lado de Firestore.
2. Si persiste: DevTools → Console → copiar el mensaje **completo**, o abrir el link del `create_composite`, que muestra colección y campos ya cargados en el formulario.

## 2. Cambios

### Parte 1 — Fallback sin índice en `cargarTCReciente` (`src/datos/tcDiario.ts`)

`tcDiario` tiene un documento por día y el id **es** la fecha (`YYYY-MM-DD`), así que ordena lexicográficamente igual que cronológicamente. Leer la colección entera y ordenar en cliente no necesita ningún índice — es exactamente lo que ya hace `cargarEstadoTcDiario` (`tcDiario.ts:59-61`), que funciona hoy en la card de Patrimonio.

```ts
export async function cargarTCReciente(n = 10): Promise<TCDiarioItem[]> {
  const aItem = (d: { id: string; data: () => any }): TCDiarioItem => ({
    fecha: d.id,
    tcUsdArs: d.data().tcUsdArs as number,
    origen: d.data().origen as TCDiarioItem['origen'],
  });

  try {
    const snap = await getDocs(
      query(collection(db, 'tcDiario'), orderBy(documentId(), 'desc'), limit(n)),
    );
    return snap.docs.map(aItem);
  } catch (err) {
    // F9.113 — fallback sin índice: el id ES la fecha (YYYY-MM-DD), así que ordenar en
    // cliente da el mismo resultado. La colección es chica (un doc por día) y es la misma
    // lectura completa que ya hace cargarEstadoTcDiario. Preferimos leer de más antes que
    // dejar la pantalla sin valor de TC.
    console.warn('[cargarTCReciente] consulta ordenada falló, uso fallback sin índice:', err);
    const snap = await getDocs(collection(db, 'tcDiario'));
    return snap.docs
      .map(aItem)
      .sort((a, b) => (a.fecha < b.fecha ? 1 : -1))
      .slice(0, n);
  }
}
```

El `catch` es genérico a propósito: sirve para el error de índice, para un fallo de red transitorio y para lo que venga. Si el fallback **también** falla, la excepción sube y la maneja la Parte 2.

### Parte 2 — Que el error sea accionable (`src/vistas/perfil/TipoCambio.tsx`)

1. **No dejar el histórico mintiendo.** Con `errorCarga`, el bloque del histórico no puede decir `ÚLTIMOS 0` / `Sin histórico todavía`: tiene que decir `No se pudo leer el histórico.` y ofrecer **Reintentar** (`onClick={recargar}`, que ya existe).
2. **Mensaje humano + detalle plegado.** En vez del volcado crudo:
   > `No se pudo leer el tipo de cambio. Podés cargarlo a mano acá abajo.`

   y debajo un `<details>` con `<summary>Ver detalle técnico</summary>` que contiene `errorCarga` con `wordBreak: 'break-all'`, `fontSize: 11`, `userSelect: 'text'` → así se puede leer y copiar sin romper el layout.
3. **Dejar claro que escribir sigue andando.** La card *Cargar / corregir TC manual* ya funciona (`actualizarTCManual` es una callable, no depende de esta consulta). Con `errorCarga`, agregar arriba del formulario una línea 11.5px en `var(--gf-gray-400)`: `La carga manual funciona igual — la lectura del histórico es lo que falló.`

Sin la Parte 1 esto no alcanza, y sin la Parte 2 el próximo fallo vuelve a dejar la pantalla muda. Van juntas.

### Parte 3 — Índice, **sólo si** el diagnóstico de §1.2 lo justifica

Si con bundle limpio el error persiste y el texto completo identifica una consulta legítima que necesita índice compuesto:

- Agregar el índice a **`firestore.indexes.json`**, no sólo por consola.
- **Motivo, importante:** `firestore.indexes.json` es la fuente de verdad del deploy. Un índice creado a mano por el link de la consola no está en ese archivo, y un `firebase deploy` posterior puede proponer borrarlo. Si se crea por consola para desbloquear, hay que replicarlo en el archivo en el mismo commit — si no, vuelve a romperse solo más adelante y va a parecer un bug nuevo.
- Desplegar con `firebase deploy --only firestore:indexes` y esperar a que el índice quede `Enabled` (tarda unos minutos) antes de dar por cerrado.

## 3. Criterios de cierre

1. `npx tsc --noEmit` sin errores nuevos sobre el baseline. `npm run build` OK.
2. *Perfil › Tipo de cambio* muestra el valor del TC y el histórico **aunque la consulta ordenada falle**. Forzarlo temporalmente (por ejemplo, tirando un throw en la rama del `try`) para comprobar que el fallback entra y que en consola aparece el `console.warn`.
3. Con la lectura rota de punta a punta: se ve el mensaje humano, el detalle técnico se despliega y se puede copiar, aparece **Reintentar**, y el histórico **no** dice `Sin histórico todavía`.

5. Diagnóstico de §1.2 registrado en el reporte: si era bundle cacheado, decirlo explícitamente y cerrar sin tocar índices.
6. Deploy `--only hosting` y verificación en incógnito (o *borrar datos del sitio*).
