# F9.140 — Una sola definición de "pago cubierto"

## Contexto

Reportado: una factura de ITPA SA se pagó el 11/8, el comprobante quedó `vinculado` con badge
"Pagó una factura", y la app la sigue mostrando vencida.

Diagnosticado con `scripts/auditF9139.ts` contra producción (14/8). No era ninguna de las dos
hipótesis que se venían siguiendo: ni `tipoDocumento` mal clasificado, ni prioridad de fecha
invertida en `confirmadoPagoPorFecha`. Ambas quedan descartadas con dato:

```
comprobante 3f3ba8e8… · tipoDocumento="transferencia" · esObligacionDoc=false
  fecha usada (venc[0].fecha ?? fecha) = "2026-08-11"
  quedaConfirmado = true
```

`confirmarRama1` hizo lo correcto. El defecto está en otro lado, y son dos cosas encadenadas.

### 1. El dato: un par imposible que se regeneró

`movimientos/PHWX7clkikjA17bz4sst` (mes 2026-08, ITPA SA, $2.003.500):

```
pagado         = false
confirmadoPago = true
pagadoEn       = 2026-08-12
actualizadoEn  = 2026-08-12T00:40:19.376Z
```

Bajo la semántica de `docs/CLAUDE.md` ese par es imposible: `confirmadoPago` = alguien verificó
que la plata salió; `pagado` = la plata salió. No se verifica lo que no pasó.

Esa terna —`confirmadoPago` y `pagadoEn` escritos, `pagado` no— es la huella exacta de
`confirmarRama1` **anterior** a F9.138. Verificado en `525f21d^:src/datos/comprobantes.ts`:

```ts
...(esObligacionDoc(...) ? {} : { confirmadoPago: quedaConfirmado,
     ...(quedaConfirmado ? { pagadoEn: serverTimestamp() } : {}) }),
```

El código actual escribe `pagado`, `confirmadoPago` y `pagadoEn` en el mismo literal: no puede
producir `pagadoEn` sin `pagado`. O sea que el 12/8 corrió bundle pre-F9.138 (deploy posterior a
esa fecha, o service worker cacheado). Es el décimo caso del incoherente que F9.138 limpió —
encontró 9, los arregló, y declaró el defecto cerrado.

### 2. El código: dos pantallas, dos definiciones de "cubierto"

`src/vistas/Resumen.tsx:486`, sección de vencidos de la Card 1:

```ts
.filter(m => m.tipo === 'Gasto' && m.pagado !== true && fechaEfectivaMov(m) < inicioHoy)
```

Solo mira `pagado`. `fechaEfectivaMov` toma `vencimientos[0].fecha` = 2026-08-10 < hoy → entra
a vencidos.

`src/datos/checklist.ts` usa otro criterio: `pagado === true || confirmadoPago === true`. Por eso
el audit reporta **0 vencidos** y el ítem "Educación y chicos › Colegio Fede" en `pagado` en julio
y en agosto, mientras la Card 1 lo pinta rojo.

**Este código está en HEAD.** F9.136 §5 auditó exactamente este cruce sobre TELECOM y lo dejó sin
arreglar. Deployar F9.136+137+138 no lo toca.

Con el par coherente el síntoma no aparece: mientras `pagado` y `confirmadoPago` vayan juntos,
los dos predicados coinciden. Por eso el defecto sobrevivió — solo se manifiesta cuando el dato
se rompe. Arreglar el dato sin arreglar el predicado deja la bomba armada.

## §1 — Un solo predicado

**Auditar antes de tocar:** `tieneCobertura` es local a `checklist.ts` y opera sobre los matches
de un ítem, no sobre un `Movement` suelto. Leer su firma real antes de exportarla. Si no sirve
tal cual, extraer el predicado a una función nueva y que `tieneCobertura` la use — **no duplicar
la condición**, que es el defecto que este spec viene a cerrar.

En `src/datos/checklist.ts`:

```ts
// F9.140 §1 — un movimiento está cubierto si la plata salió (`pagado`) o si alguien verificó
// que salió (`confirmadoPago`). Exportado porque Resumen.tsx lo necesita: tener dos
// definiciones de "cubierto" en dos pantallas fue exactamente el defecto.
export function movimientoCubierto(m: Pick<Movement, 'pagado' | 'confirmadoPago'>): boolean {
  return m.pagado === true || m.confirmadoPago === true;
}
```

En `src/vistas/Resumen.tsx`, reemplazar `m.pagado !== true` por `!movimientoCubierto(m)` en:

- `:477` — `aPagarHoy`
- `:486` — `aPagarVencidos`

**Leer el comentario de `:470` antes de tocar `:477`.** Dice, a propósito, que los `pagado: true`
sin confirmar **no** entran a "a pagar": esa plata ya salió y lo que falta es confirmarla, que es
otro problema. Sigue siendo cierto y el cambio no lo rompe — `movimientoCubierto` los sigue
excluyendo. Lo que agrega es el caso inverso. **Actualizar ese comentario** para que describa las
dos direcciones; si queda como está, el próximo que lo lea va a creer que el predicado solo mira
`pagado`.

**No tocar `:459`** (`pagadosHoy`, Card 2). Ahí `pagado === true` es la pregunta literal —"¿qué
plata salió hoy?"— y no es proxy de nada. Mismo criterio que F9.137 §3 aplicó a `agenda.ts:74`,
`Notificaciones:70` y `Resumen:993`: preguntar por el campo está bien cuando lo que se quiere
saber ES el campo.

Barrido: `grep -rn "pagado !== true" src/` y `grep -rn "pagado === false" src/`. Revisar cada uno
con ese criterio y reportar cuántos se cambiaron y cuántos se dejaron, con el porqué de los que
se dejan. F9.136 barrió solo `src/vistas` y por eso F9.137 tuvo que volver — el barrido es sobre
todo el repo.

## §2 — Que el par imposible no se pueda escribir

Hoy nada lo impide. `src/datos/movimientos.ts` tiene cuatro writers que ya lo hacen bien
(`:215`, `:238`, `:288`, `:304` — los tres campos juntos, en las dos direcciones), pero eso es
disciplina, no invariante: F9.138 arregló dos writers y el par volvió igual por un tercero,
cuatro días después.

Guard en `src/datos/movimientos.ts`, aplicado por todos los writers de pago antes de escribir:

```ts
// F9.140 §2 — `confirmadoPago: true` con `pagado: false` es imposible: no se puede verificar
// una salida de plata que no ocurrió. F9.138 arregló dos writers y el par reapareció el
// 2026-08-12 por un tercero. Esto lo corta en el punto de escritura, no en la limpieza.
```

Reglas:

- **Corrige** (fuerza `pagado: true`), no tira error. Un throw acá deja al usuario sin poder
  confirmar un pago, que es peor que el par incoherente.
- Loguea `movimientoId` y el writer que lo disparó. Sin eso, la corrección silenciosa esconde al
  writer culpable — que es exactamente cómo este defecto sobrevivió a F9.138.
- Fail-soft: nunca romper una escritura del usuario por esto.

**No replicarlo en reglas de Firestore.** Necesita leer el doc previo, sale caro en reglas y deja
una tercera copia de la semántica en un lenguaje distinto.

### Decisión ABIERTA

El log a consola muere con la sesión del browser. Si se quiere rastro durable de cada corrección
—un campo `corregidoPorInvariante: true` en el doc, o un `console.error` que llegue a
`functions`— hay que decidirlo antes de implementar, porque cambia si esto es solo cliente o
también server. **Sin respuesta explícita, implementar solo el log a consola** y anotar la
limitación en `docs/CLAUDE.md`: el próximo writer roto se va a descubrir con un audit, no en el
momento.
