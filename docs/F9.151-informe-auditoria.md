Los pasos 1-5 los sabe deshacer `descartarEntrada` (1581-1660): borra los movimientos con
`origenComprobanteId === id`, revierte los preexistentes (`hashPdf:null`, `refStoragePdf:null`,
`confirmadoPago:false`, `itemEsperadoId` borrado, destinos a null), borra `entrantes/{id}` y el doc
destino. **El paso 6 no lo deshace nadie**: devuelve `advertenciaDestino` y la UI te dice "revisá
/destinos manualmente" (`src/vistas/Comprobantes.tsx:829-831`). Y **borra el blob de Storage**
(1653-1656), que es justo lo que una reclasificación no debe hacer.

**El `hash` como doc id sí permite recrear sin colisión.** Son colecciones distintas
(`comprobantes/{hash}` y `resumenesTarjeta/{hash}`), el id es el SHA-256 del archivo, y
`crearDocResumen` (1383-1414) escribe un doc nuevo entero. La idempotencia del router
(`functions/src/index.ts:1436-1449`) chequea las dos colecciones, así que si dejás las dos pobladas
el router futuro tomaría `comprobantes` primero. `refStoragePdf` es el mismo path (`entrantes/{hash}`)

`resumenesTarjeta/{hash}` con `estado:'subido'` dispara `extraerResumenTarjeta` (1273, onCreated)
solo: la reclasificación no necesita un trigger nuevo, necesita un callable que limpie 1-6 y cree el
doc en la otra colección.

**Consecuencia observable:** si el router se equivoca y vos no lo corregís en el momento (o no te da
la card de `ambiguo`), no hay camino de vuelta desde ninguna pantalla.
